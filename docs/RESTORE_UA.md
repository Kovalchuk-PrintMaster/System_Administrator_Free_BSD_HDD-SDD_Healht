# Відновлення вихідного файлу на FreeBSD

> **Увага:** це процедура відновлення архівного **джерела**, а не підтверджений запуск моніторингу. В оригінальному коді знайдено функціональні прогалини. Не запускайте `short`, `long` або `install` до окремого рев’ю адаптації FreeBSD та реального середовища.

## 1. Отримайте GitHub-репозиторій

На окремій перевіреній машині: `git clone https://github.com/Kovalchuk-PrintMaster/System_Administrator_Free_BSD_HDD-SDD_Healht.git`. Якщо старий FreeBSD не підтримує актуальний TLS/GitHub, завантажте архів репозиторію на сучасному комп'ютері й перенесіть захищеним способом. Не встановлюйте застарілу TLS-інфраструктуру лише заради цього.

## 2. Перевірте ідентичність файлу

У директорії репозиторію перевірте контрольну суму з `docs/original-script.sha256`:

```sh
sha256 -q disk_health_audit.sh
cat docs/original-script.sha256
```

Порівняйте обидва SHA256 (у другому рядку хеш перед назвою файлу). Якщо доступний Bash, `bash -n disk_health_audit.sh` перевіряє лише синтаксис, **не працездатність**.

## 3. Безпечно поверніть файл

Лише після огляду на цільовому сервері:

```sh
sudo /bin/sh -c 'install -d -m 700 /root/forprint-utils/disk-health-audit'
sudo install -m 700 disk_health_audit.sh /root/forprint-utils/disk-health-audit/disk_health_audit.sh
```

**Не копіюйте поверх наявного справного файлу без незалежного бекапу та порівняння!** На цільовому сервері спочатку збережіть поточну версію.

## 4. Відновіть секрети ОКРЕМО

`disk-health-audit.env` відсутній у публічному репозиторії навмисно. Відновіть його тільки зі свого захищеного резервного сховища (не через GitHub) із правами `600`, власник `root`. Шаблон `config/disk-health-audit.env.example` не містить діючих реквізитів.

У коді фактичний `ENV_FILE` за замовчуванням — `$PROJECT_ROOT/config/disk-health-audit.env`, а `PROJECT_ROOT` за замовчуванням `/opt/forprint-utils/disk-health-audit`; вихідний `.env` у файлі інвентаризації був поруч зі скриптом у `/root/...`. Потрібно **відновити реальний спосіб передачі `ENV_FILE` / `PROJECT_ROOT` і звірити точні шляхи**. Не припускайте, що система автоматично підхопить `.env` поруч зі скриптом.

## 5. З'ясуйте і поверніть реальне планування

Поточний архів не містить `root crontab`, `/etc/crontab`, `periodic`, `rc.conf`, параметрів окремого сервісу, зовнішніх сценаріїв або звітів. Не створюйте нових розкладів до з'ясування вихідного механізму: це могло б запустити дублікати SMART self-test.

Рекомендована інвентаризація **тільки для локального огляду**, з редагуванням секретів перед передачею звітів третім особам:

```sh
sudo crontab -l
sudo grep -R -n 'disk_health_audit\|disk-health-audit' /etc/crontab /etc/periodic /usr/local/etc/periodic /usr/local/etc/rc.d 2>/dev/null
```

На FreeBSD 10 root shell часто `csh`/`tcsh`. Для багаторядкових POSIX shell-блоків запустіть `/bin/sh`; сам оригінальний скрипт — Bash і вимагає `bash`, не `sh`.

## 6. Контроль безпечного повернення

Перевіряйте спочатку на тестовому хості/копії; не запускайте записуючі/довгі SMART self-tests на робочих дисках заради перевірки резервної копії. Перед будь-яким production-запуском потрібно розв'язати проблеми з `ASSESSMENT_UA.md` і звірити залежності (`bash` з associative arrays, `smartctl`, `flock`, інші FreeBSD відмінності), scheduler, логи, Telegram та сценарій відкату.
